## 2026-04-29 — Bugfix: run-crash array caps + Geometry tab error messaging

- Actor: Claude Opus 4.7 (claude-code)
- Summary: Two reported bugs investigated; one root cause confirmed and fixed, the other turned out to be a UX/visual issue rather than a code defect. (1) **Run crash mid-stream** was a renderer OOM caused by unbounded array growth in `renderer/store/useRunsStore.ts`: every SSE `log` and `residual` event spread-cloned the existing array (`[...state.log, e.line]`), giving O(N²) memory churn. With 10–50k log lines per cavity run, a non-virtualized `LogsTab.tsx` rendering a `<div>` per line, and a re-derived residuals array forcing `ResidualChart` to re-render on every event, the V8 heap exhausted within 2–5 minutes. Fix: capped `log` at 5000 lines and `residuals` at 2000 points with amortized trimming — only slice when length exceeds 1.5× the cap, so the per-event cost is O(1) at steady state. The on-disk `runs/<runId>.log` remains the authoritative full log, so historical run views are unaffected. Trimming drops oldest entries. **Verified live in Playwright:** ran the lid-driven cavity case, run completed in 19s with status `success` and exits 0/0/0; renderer heap stayed at 27MB (limit 4096MB); DOM held 7187 log lines (one trim cycle below the 7500 threshold) while the on-disk log had 9694 lines — confirming the cap was actively trimming. (2) **Geometry "blank screen"**: initial Explore-agent analysis suggested foamToVTK output had no patch files (only top-level UNSTRUCTURED_GRID `cavity_<step>.vtk`) because its `find ... | head -30` was truncated. Direct verification via `/api/projects/:id/vtk/manifest` showed the legacy `-ascii` foamToVTK actually does emit per-patch POLYDATA subdirs (`fixedWalls/fixedWalls_<step>.vtk`, `movingWall/movingWall_<step>.vtk`), classified correctly as `kind: 'patch'` by the existing manifest walker. Playwright screenshot of the running app shows the boundary patches **do render** as a faint square outline with the legend (fixedWalls blue, movingWall amber). The user's "blank screen" report most likely reflects the very low contrast of the rendering: dark theme background `[0.07, 0.08, 0.1]`, dim edge color `[0.15, 0.17, 0.2]`, and the cavity's internal volume being intentionally empty (vtk.js v35 ships no `XMLUnstructuredGridReader` / `GeometryFilter`, so internal cells can't be rendered). Confirmed live (screenshot before/after), then reverted. Kept the small UX win: when no patch files are present, `GeometryTab.tsx` now shows an explicit error message ("Legacy ASCII mesh detected — re-run…" / "Internal mesh present but no boundary patches found…") instead of the silent "No mesh yet" overlay, so any genuinely empty case is no longer indistinguishable from a render failure.

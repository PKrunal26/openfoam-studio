OpenFOAM Studio is an AI desktop app that turns a sentence like “simulate lid-driven cavity flow” into a complete, runnable OpenFOAM case — then meshes it, solves it, and fixes its own errors.

Electron · React · TypeScript Local server · SSE streaming Docker · OpenFOAM 13 Bring-your-own-model

01 The core idea

Computational fluid dynamics without the boilerplate

OpenFOAM is powerful but unforgiving — a single case is a tree of finely-formatted dictionary files, and one wrong keyword aborts the solver. OpenFOAM Studio puts an AI agent between you and that complexity.

You describe the physics in words. The agent writes every case file, runs the simulation inside a sandboxed container, watches the solver logs, and when something breaks it diagnoses the failure and patches the case — looping until it converges or it has tried enough.

01 — DESCRIBE

You write a prompt

“Lid-driven cavity, Re = 100.” The request streams to a local server, which hands it to the generation agent.

02 — GENERATE & RUN

The agent builds the case

It reads docs, writes the eight dictionary files, smoke-tests the mesh and solver, then runs the full simulation in Docker.

03 — RECOVER & SEE

It heals, you observe

Known errors are auto-patched and re-run. Results stream back live — logs, residual curves, and 3-D geometry.

02 System architecture

Five layers, one process tree

A native Electron shell launches a small HTTP server as a child process. The React UI talks to that server over HTTP and Server-Sent Events; the server orchestrates the reusable core/ modules, which in turn drive Docker, the chosen LLM, and the project files on disk.

03 End-to-end data flow

One open request, a stream of events back

Every long operation runs as a single HTTP request that stays open while the server pushes back a stream of typed events — so the UI updates live instead of polling. First, how the stream works; then the four flows that ride on it.

04 The generation agent

A tool-calling loop, not a single guess

Rather than asking the model for one giant JSON dump of files, the agent is handed a toolkit and left to iterate — reading docs, writing files, and actually running the mesher and solver to check its own work. The loop ends when the model calls finish or hits a 12-step cap.

FILE TOOLS

Write, don't dump

Each file is produced with write_case_file or surgically changed with edit_case_file. Paths are guarded inside case/ and CRLF is normalised to LF on write.

DOC TOOLS

Grounded in real docs

search_docs queries an index of the OpenFOAM 13 guide plus the project wiki, returning ranked snippets the agent can open in full with read_doc.

RUN TOOL

Verifies its own work

run_command executes blockMesh, checkMesh, or a short foamRun smoke-test in Docker — so the case is proven to solve before you ever press Run.

05 Knowledge retrieval

Keyword search, no vector database

The corpus is small enough that dense embeddings add cost without accuracy. Instead, markdown is split at heading boundaries into chunks, indexed by a lightweight full-text engine, and returned as citation-style hits the agent can expand.

Chunked at H1/H2/H3

Each chunk keeps its heading hierarchy, so a hit reads like a breadcrumb: cases › cavity › boundaries.

Ranked, de-duplicated hits

FlexSearch indexes heading, body, and path; results are merged and capped at k snippets per query.

Two sources, one index

Scans docs/openfoam-v13/ and wiki/; every hit is tagged with its source so the agent knows what it is reading.

Path-guarded reads

read_doc only resolves files under the two allowed directories — nothing outside the knowledge base can be opened.

06 The run pipeline

Mesh, export, solve — in one sandboxed sweep

Pressing Run executes three OpenFOAM commands in sequence inside the container. Each line of output is streamed to the UI and written to a per-run log; residual lines are parsed on the fly into a live convergence chart.

07 Self-healing error recovery

When the solver aborts, the app debugs itself

A FOAM FATAL ERROR doesn't end the story. The log is matched against known failure classes; a recognised error produces a precise file patch. The fix is applied, the retry counter ticks up, and the run restarts — up to three times before it gives up.

08 Safety & the sandbox

The agent is powerful, but it is fenced in

An autonomous agent writing files and running commands needs hard boundaries. OpenFOAM Studio never exposes a raw shell — every action passes through a narrow, audited surface.

01

Command allowlist

Only a fixed set — blockMesh, checkMesh, foamRun, foamToVTK and a few solvers — can reach Docker. Anything else throws.

02

Path containment

Every file path is resolved and checked to stay inside the project's case/ directory. Absolute paths, .. escapes and NUL bytes are rejected.

03

Container isolation

OpenFOAM runs in a throwaway container with only the case folder bind-mounted at /cavity. The container is stopped and removed after each command.

04

Format discipline

Files are written with path.join and forced to LF line endings — OpenFOAM rejects CRLF — so generated cases are portable across macOS, Linux and Windows.

09 Bring-your-own-model

Your key, your provider, your choice

A single resolver maps the active provider to the right client. Cloud providers run the full tool-calling agent; a local model falls back to file-by-file generation; and if you already use Claude Code, the CLI works with no API key at all.

Why three engines

Local models can't reliably honour toolChoice: 'required' or emit eight files in one response without truncating — so the local path generates each dictionary in a separate call, while cloud providers get the full doc-search-and-smoke-test loop.

10 How a project is stored

Everything lives in one folder on disk

There is no database. A project is a directory: metadata, the OpenFOAM case, and append-only logs of every run and command. It is fully inspectable, portable, and easy to back up.

demo/projects/<id>/
├─ meta.json — name, status, retryCount, chat messages[]
├─ case/ — the OpenFOAM case the agent writes
│ ├─ 0/ — initial & boundary fields (U, p)
│ ├─ constant/ — physical & transport properties
│ └─ system/ — controlDict, fvSchemes, fvSolution, blockMeshDict
├─ runs.jsonl — one record per run (status, exits, timing)
├─ commands.jsonl — one record per command executed
└─ runs/<runId>.log — full captured output of a run
META

State of record

The status field drives the whole UI — idle → generating → ready → running → done / error — and the message list is the chat history the agent reads on refinement.

JSONL

Append-only history

Runs and commands are never rewritten, only appended. The history panels read these newest-first, so nothing about a past run is ever lost.

LOGS

Replayable output

A finished run's complete log is on disk, so the UI can show exactly what the solver printed without re-executing anything.
